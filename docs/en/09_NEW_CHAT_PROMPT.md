## Testing and release discipline
Use isolated synthetic projects/profiles and disposable Windows runners for installer tests. Keep current-format, native dependency audit, security, UI, functional, packaging and actual installer/Portable gates; never weaken a failed assertion. No repeat extended load/comparative runs for unchanged stable 2.5.0. Existing benchmark scripts are available for deliberate, approved future measurement. Do not imply full-program coverage or perfect security. Build independently from the public source; never copy private history, links, IDs, logs or credentials. No force pushes, unapproved publishing or destructive cleanup. Keep previous releases and verified assets. Future changes require agreed scope, a separate branch, tests, updated bilingual documentation and acceptance before release.

## Maintenance
Keep EN/RU handover, status, changelog and relevant documents up to date whenever approved work changes them. Distinguish source changes from documentation and administrative settings. Report exact commits, verified CI and release results, outstanding items and access limits. Do not claim completion for pending work or promise work in the background. The project is documented so a new chat can continue from the repositories, not from remembered conversation.
